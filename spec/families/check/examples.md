# Define a Check through discriminating examples

Use this optional approach when concrete inputs, actions, and expected outcomes
make a proposition assessable. Select examples because they distinguish an
acceptable implementation from plausible violations of the supported promise.
A longer list of similar cases can leave the same underlying ambiguity intact.

## Develop the criteria

Identify the promise and its relevant context. Establish the actor, starting
state, inputs, action, observable outcome, and important side effects where they
affect the result. Explain what each selected class of examples contributes:
ordinary success, valid boundary behavior, rejection, interruption, or interaction
with existing state. Those classes are choices driven by the promise.

Give expected results a basis independent of the implementation under examination.
Explain where reference values or judgments come from. A fixture generated by the
same rule being examined can reproduce its mistake. If an example relies on a
separately calculated result or a known reference case, make that basis available
in the definition's explanation without publishing implementation evidence in
Intent.

State the discriminating observations. A command returning success can coexist
with an absent side effect, an incomplete result, or a forbidden state change.
Identify the material needed to establish each applicable observation. Describe
what refutes the proposition and when missing setup, unavailable material, or
ambiguous observations leave it unassessed or inconclusive.

Explain the limits of example coverage. Finite examples may leave broader inputs,
different configurations, or long sequences unexamined. A particularly revealing
case can become a Falsifier, but naming it does not prove that every violation
will be detected. Narrow the conclusion honestly without erasing the supported
Knowledge's remaining obligations.

## What richer information adds

“Invalid tokens are rejected” permits an implementation that rejects every token.
When the promise includes useful acceptance, add valid reference tokens with
independently established accepted results, alongside invalid and boundary cases.
A generator and validator agreeing on tokens they produce together can conceal
a shared defect. The definition needs a basis that can distinguish agreement
from the intended validity rule.

“The import command succeeds” permits an implementation that exits successfully
without importing anything. Criteria can distinguish accepted, rejected, and
duplicate rows, establish expected persisted values, and explain how input totals
relate to reported results. If the promise includes atomicity, a failing row or
interruption can distinguish a complete rollback from a partial import.

Use a case table where comparison helps, or a short setup/action/outcome narrative
where state transitions need explanation. Do not make every example repeat a
large form whose fields have no bearing on that case.

## Judge the result

Apply the written Pass criteria to an always-reject implementation, a constant
answer, a special case for the examples, and an omitted side effect when relevant.
Name the criterion that excludes each useful counterexample. Repair remaining
gaps or state their limits using the stable
[Check review guidance](../../guidance/check-review.md).

Use the [common Check guidance](../../guidance/check.md) and
[Check contract](../../spec/CHECKS.md). Examples organize definition prose; they
do not create an executable suite, authorize examination, or report a result.
